# In-app screenshot-to-canvas

## Architecture

1. The editor toolbar calls `SnoteScreenCapture.captureDisplay()` over the `com.snote/screen_capture` Flutter method channel.
2. Android opens the OS-owned MediaProjection consent sheet. The user must approve capture; Snote does not attempt to bypass Android's screen-capture permission or secure-window protections.
3. The generated beta Android runner starts a short-lived foreground service with the `mediaProjection` service type. The service creates a one-frame virtual display and reads pixels through `ImageReader`.
4. The frame is cropped for row-stride padding, encoded as PNG bytes in memory, and returned through the method channel. It is not written to `MediaStore`, the gallery, or a temporary image file.
5. The Flutter editor computes a centered canvas placement and stores the bytes in the current page's editable image-asset list. The normal note-save path persists the asset with the note, and existing image selection handles can move/resize it.

## Platform behavior

- **Android:** Captures the device display, including other visible apps in split-screen when Android includes them in the projection. Every capture is user-consented. Apps/windows marked secure by their owners may be blanked by the operating system.
- **iOS:** Snote uses a Flutter render-boundary capture of the active Snote canvas. iOS does not permit an ordinary app to silently read another app's screen. Capturing a system-wide display requires a user-started ReplayKit broadcast extension; that is a separate extension-level workflow and is not represented as silently supported here.
- **Desktop/Web:** Falls back to capturing the Snote page render boundary, rather than claiming system-wide capture permissions that those platforms do not grant through this Flutter method channel.

## Implementation location

- Dart bridge: `app/lib/features/tools/screen_capture.dart`
- Editor insertion and toolbar triggers: `app/lib/features/notes/editor_v2/editor_v2_page.dart`
- Generated Android activity/service and manifest wiring: `.github/scripts/configure_beta_android.py`, invoked by `.github/workflows/beta.yml`. The Android runner is generated by CI, so native capture sources and permissions are injected there before compiling the beta APK.


## Code path

The Flutter bridge is intentionally tiny. It returns raw encoded bytes, not a gallery URI:

```dart
class SnoteScreenCapture {
  static const MethodChannel _channel =
      MethodChannel('com.snote/screen_capture');

  static Future<Uint8List?> captureDisplay() =>
      _channel.invokeMethod<Uint8List>('captureDisplay');
}
```

The active editor checks that the page is unlocked, calls the bridge, computes a centered rectangle that fits the current paper, then calls the existing image-insertion path:

```dart
final bytes = await SnoteScreenCapture.captureDisplay();
if (!mounted || bytes == null || bytes.isEmpty) return;

await _insertImageBytes(
  bytes,
  name: 'Snote screen capture.png',
  x: (1 - widthRatio) / 2,
  y: (1 - heightRatio) / 2,
  width: widthRatio,
  height: heightRatio,
);
```

The native Android entry point asks the OS for its projection-consent token before starting the capture service:

```kotlin
val manager = getSystemService(Context.MEDIA_PROJECTION_SERVICE)
    as MediaProjectionManager
startActivityForResult(
    manager.createScreenCaptureIntent(),
    REQUEST_SCREEN_CAPTURE,
)
```

The service uses `MediaProjection.createVirtualDisplay(..., imageReader.surface, ...)` and `ImageReader.acquireLatestImage()`. It handles row-stride padding, builds an in-memory `Bitmap`, encodes the image with `Bitmap.compress(PNG, ...)` into a `ByteArrayOutputStream`, and returns those bytes over the method channel. The code is in the generated-runner setup script so CI installs it into the Android runner before the APK is compiled.

## Implementation steps

1. Trigger **Capture screenshot to canvas** in the editor title bar or floating toolbar.
2. On Android, accept the OS capture prompt and select full-display sharing when the system offers a choice. This can include other visible apps in split-screen; secure windows may remain blank.
3. The capture service reads a frame and returns PNG bytes directly to Flutter. It writes no standalone screenshot file to shared storage and does not add anything to the gallery.
4. The editor inserts those bytes into the active page as an image element, centered and sized to fit the page; users can select, move, resize, and save it with the note.

The image is memory-only during capture. Once inserted, Snote persists the image as part of the note so it survives closing/reopening the document; this is distinct from saving a screenshot file to the device gallery.

## Validation checklist

- Grant capture permission, capture a split-screen display, verify the resulting PNG includes visible display content and lands centered on the active page.
- Cancel the system consent dialog and verify Snote reports cancellation without adding an image.
- Confirm the device gallery does not gain a new screenshot.
- Lock the current page and confirm capture/insertion is rejected.
- Confirm the new image can be selected, moved, resized, saved, closed, and restored with the note.
- Test memory use and timeouts on high-resolution displays; secure surfaces are controlled by Android, not by Snote.
