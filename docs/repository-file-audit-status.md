- This table is a live audit tracker, not a claim that every source file has been semantically audited.
- **Audited (prior ledger)** means a prior ledger explicitly records implementation and caller review.
- **Partial review** means focused implementation paths were inspected; it must not be treated as a full file audit.
- **Static import scan only** means import/export statements and lifecycle markers were extracted from all tracked Dart library and test files. This does not prove every symbol is used correctly or that callers/platform runtime dependencies are fully understood.
- **Not audited** means source-level review is still pending.
- **Blocked — binary/runtime asset** means binary contents or actual runtime loading behavior is not established by the Git tree alone.
- Files generated by Flutter/Gradle/CocoaPods during CI are not tracked blobs and must be audited through generated build output when relevant.

## Audit order and gates

1. Canvas input/rendering, stroke model/codec, persistence and note restoration.
2. Editor routes and lifecycle; trace all callers before splitting large widgets.
3. PDF open/render/annotation/scroll/cache/disposal paths.
4. Dependency declarations, lockfile, plugin registration, manifests and generated merged manifests.
5. CI, beta and release workflows, including output artifacts and secrets handling.
6. Website routes, API handlers, assets, CSS and build configuration.
7. Remaining tools/settings/features, tests and docs.

No runtime change should be made solely to reduce source-file size. For every proposed code or dependency change, record callers, platform/runtime dependencies, focused tests, full relevant CI, and comparable artifact/performance measurements. Preserve stylus latency/pressure/palm rejection, stroke persistence/undo-redo, offline-first data, note restoration, PDF rendering/navigation, and cross-platform support.

## Findings from the source-level pass

- **Confirmed direct-dependency candidates:** `flutter_riverpod` and `collection` have no imports in the tracked app library or test source. Their removal is isolated in PR #40 and is not considered safe/complete until dependency resolution and all CI builds pass. `collection` may remain transitively.
- **Retained overlapping PDF packages:** `pdf` is used for PDF generation/export, while `pdfx` is used for PDF viewing/rendering and annotation. Both appear in editor code; they are not duplicates by name alone.
- **Retained web view:** `flutter_inappwebview` is imported by `web_search_panel.dart`. The previously removed `webview_flutter` has no tracked source import.
- **Cache bounds:** the PDF raster cache in Editor V2 is limited by entry count and a byte cap, and its raster-future cache is limited to 12 entries. Background/image byte caches and PDF source byte caches have no obvious local size cap in the inspected paths; treat them as profiling candidates, not proven leaks.
- **Database portability risk:** `database.dart` imports `sqflite` and calls `openDatabase`, but does not itself initialize `sqflite_common_ffi` or `sqflite_common_ffi_web`. Those packages remain in the manifest. Do not remove them until intended desktop/web database initialization and runtime persistence are verified; a successful build does not prove SQLite works.
- **Performance metrics issue:** the writing overlay previously counted missed frames against a fixed 16.667 ms threshold. A targeted correction and regression tests are proposed in PR #39; the PR must pass CI before merge. Its displayed input-to-frame timing is not a measurement of physical event-to-photon stylus latency.
- **Native Android:** custom ringtone and screen-capture MethodChannels, service, manifest permissions, share intents and notification receivers are retained; changes require matching Dart call-site and generated merged-manifest checks.

## Device/emulator measurement blocker

No physical-device or emulator trace was available during this repository review. Consequently, actual event-to-visible-ink latency, refresh-rate-aware frame percentiles, memory growth during long writing sessions, and large-PDF open/scroll memory remain **blocked / unmeasured**. CI compilation and widget tests do not establish these runtime measurements. The repeatable protocol is in `docs/phase-six-performance-memory-baseline.md`; record device/build/document metadata and at least three runs before accepting a performance optimization.
